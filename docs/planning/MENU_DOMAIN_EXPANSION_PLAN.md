# План расширения: категории, ингредиенты, заготовки, блюда, техкарты

Дата: 2026-04-23

## 1) Текущее состояние (подтверждено по коду)

1. Модуль стартовых onboarding-вопросов уже есть: `app/services/category_onboarding.py`.
2. Он пока не подключен в runtime-поток бота/пайплайна (используется только в тестах).
3. Базовые категории по видам бизнеса уже зашиты в правила (`_BASE_CATEGORIES`, `_SEGMENT_CATEGORIES`, `_TAG_CATEGORIES`).
4. В текущем UI бота нет ручного поля для выбора/создания категории по позиции.
5. При `sync_nomenclature` категории могут создаваться автоматически через iiko API, но без пользовательского шага ручного подтверждения.

## 2) Ответ на вопрос по подходу к категориям

Ниже три реалистичных варианта.

### Вариант A: только предопределенные категории по типу бизнеса

- Плюсы: быстро, детерминированно, без лишних кликов.
- Минусы: у нового клиента с уникальной терминологией может быть много “непопаданий”.

### Вариант B: первый запуск -> пользователь вводит свои категории (через пробел), шаг можно пропустить

- Плюсы: сразу получаем язык клиента.
- Минусы: риск мусорных и дублирующихся названий, нужен слой нормализации.

### Вариант C (рекомендуемый): гибрид

1. Строим базовый набор из правил по виду бизнеса.
2. Показываем шаг “добавьте свои категории” (опционально, можно пропустить).
3. Перед первым sync выполняем смысловой merge с существующими категориями iiko.
4. Новые категории показываем к подтверждению (или замене) перед созданием.

Итог: и скорость, и контроль.

## 3) Про “общий банк категорий”

Рекомендовано внедрить двухуровневую модель:

1. `global_category_bank` (глобальные canonical-имена, алиасы, usage_count).
2. `tenant_category_map` (привязка клиента к canonical и реальному category_id в iiko).

Минимальные поля:

- `canonical_name`
- `aliases[]`
- `source` (`system`, `owner`, `support`, `auto`)
- `approved` (bool)
- `last_used_at`
- `created_by_user_id` (если есть)

Правило обновления:

- все новые категории, созданные системой/клиентом/поддержкой, попадают в банк;
- но автоприменение в других аккаунтах только после валидации (иначе переносим ошибки между клиентами).

## 4) Проверка endpoint’ов и структуры меню (по факту в проекте)

### Подтвержденные endpoint’ы в текущей интеграции

- `GET /resto/api/v2/entities/products/list`
- `POST /resto/api/v2/entities/products/save`
- `GET /resto/api/v2/entities/productCategories/list`
- `GET /resto/api/v2/entities/categories/list?type=PRODUCT`
- `POST /resto/api/v2/entities/productCategories/save`
- `POST /resto/api/v2/entities/categories/save`

### Что это означает по модели данных

В текущей интеграции “категории” и “товары” разделены:

- категории идут через `productCategories/categories`;
- ингредиенты/заготовки/блюда идут как `products` с разным `type`.

В коде уже учитываются типы:

- `INGREDIENT`
- `SEMI_FINISHED` / `SEMIFINISHED`
- `DISH`
- `MODIFIER`
- `GOODS`
- `SERVICE`

То есть ваш тезис “категории, ингредиенты, заготовки, блюда” логически соответствует модели, но технически это:

1. отдельный справочник категорий;
2. единый справочник продуктов с типом.

## 5) Чего сейчас нет (gap)

1. Нет UX-экрана “ручной выбор категории по позиции”.
2. Нет шага “первый запуск: введите свои категории”.
3. Нет хранилища глобального банка категорий.
4. Нет модуля распределения строк накладной по `INGREDIENT / SEMI_FINISHED / DISH`.
5. Нет подтвержденного контура для массового создания/связки техкарт (нужен endpoint discovery).

## 6) План внедрения модулей (широкий вариант)

### Этап 0. Discovery (обязательный)

1. Подтвердить на стенде endpoint’ы для техкарт/рецептов (list/save/link) и требования к payload.
2. Подтвердить, можно ли создавать `DISH`/`SEMI_FINISHED` через текущий `products/save` с типом.
3. Зафиксировать контракт в отдельном API-matrix документе.

### Этап 1. Onboarding категорий (MVP)

1. Подключить `category_onboarding.py` в первый запуск.
2. Добавить optional-шаг “введите свои категории через запятую/перенос строки”.
3. Сохранить профиль + план категорий + факт подтверждения.

### Этап 2. Банк категорий

1. Добавить таблицы `global_category_bank`, `tenant_category_map`.
2. Логировать все созданные категории (с источником и владельцем).
3. Добавить “safe merge” (exact/alias/similarity) до создания новой категории.

### Этап 3. Распределение по типам сущностей

1. Ввести `product_type_classifier`:
   - deterministic rules;
   - LLM fallback при низкой уверенности;
   - ручной override пользователем.
2. В `sync_nomenclature` сохранять тип продукта и отправлять в iiko.

### Этап 4. Модули блюда и техкарт

1. `dish_creator` — создание блюда/модификатора.
2. `prep_creator` — создание заготовок.
3. `techcard_linker` — связка блюда с технологической картой/рецептурой.
4. Контроль зависимостей: блюдо не создается без валидной базы ингредиентов/заготовок.

### Этап 5. UX-контур перед применением

1. Review-экран:
   - Категория
   - Тип (`ингредиент/заготовка/блюдо`)
   - Ед. изм.
2. Красные блокеры:
   - нет категории;
   - нет допустимой единицы;
   - не определен тип.
3. Кнопка “Оприходовать” доступна только при отсутствии блокеров.

## 7) Критичные решения перед реализацией

1. Глобальный банк категорий: общий для всех клиентов или только “подтвержденные шаблоны”?
2. При конфликте типов (например, товар как ингредиент vs блюдо) кто приоритетнее: клиент или авто-правило?
3. Нужен ли режим “только номенклатура без создания новых категорий” для безопасного старта?
4. Нужен ли отдельный шаг подтверждения именно для техкарт (после создания блюд)?

## 8) Рекомендуемый режим запуска

Запускать по слоям:

1. Onboarding + банк категорий.
2. Типизация `ingredient/prep/dish` с ручным override.
3. Только потом автоматизацию техкарт.

Так уменьшается риск поломки учета и появляется контролируемая обратная связь от тестов.
